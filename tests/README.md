# The test suite

Five tiers, each answering a different question. The tier a test belongs in is
decided by **what it would take to make it fail**, not by which file it tests.

| tier | where | question it answers | may touch |
| --- | --- | --- | --- |
| **unit** | `packages/*/src/__tests__/`, `apps/*/src/**/__tests__/` | is this function right? | nothing outside its own package |
| **integration** | `tests/integration/` | do the packages agree? | several packages, a temp directory |
| **component** | `tests/component/` | does the surface render and respond? | a DOM (jsdom), the renderer |
| **security** | `tests/security/` | what happens on hostile input? | anything, adversarially |
| **e2e** | `tests/e2e/` | does the app work? | a real browser, a built app |

On top of those sit the **gates** (`packages/cli/src/gates/`), which are not
tests but *ratchets*: they measure the whole corpus and fail on a regression.
A test asserts a fact; a gate defends a number.

## Why the split is worth the trouble

The failure this structure exists to prevent is the one that already happened
here once: the conformance suite passed 90 assertions while testing nothing,
because its expectations were computed from the same bytes it was checking. It
looked like a green tier and was a tautology.

So each tier has a rule about what it is not allowed to do:

- **unit** may not read the corpus, the network or the clock. If it needs those,
  it is an integration test wearing the wrong label. This rule was written down
  and then broken by three suites, which read all eleven documents from the
  fast tier; they now live in `tests/integration/`.
- **integration** may not assert on values it computed with the code under test.
  An expectation is a constant, a golden file, or a measurement from a
  DIFFERENT implementation.
- **component** may not assert on implementation details — class names, hook
  call counts. It asserts what a person can see or do.
- **security** must construct its hostile input by hand. A fixture generated by
  our own writer is not an attack.
- **e2e** may not stub anything. If it stubs, it is a component test.

## What is covered, and where

The suite is organised by what a person can DO with the program, not by file.
Every row is a capability; the tests for it live in the tier that could catch
its bugs most cheaply.

| what it is | where its tests are |
| --- | --- |
| the format's reader obligations — recited text, holdings, sources, rule zero | `packages/format/src/__tests__/readers.test.ts` |
| deriving marks from a source | `packages/engine/src/__tests__/selftest.test.ts`, `holdings.test.ts` |
| the author's hand over the rules: overrides, inversion, the witness | `packages/engine/src/__tests__/overrides.test.ts` |
| writing systems and transliteration | `packages/engine/src/__tests__/script.test.ts` + the `check:transliteration` gate |
| the caret, selections, ranges, rebasing marks | `packages/edit/src/__tests__/caret|range|rebase.test.ts` |
| placing a mark by hand, and undo | `packages/edit/src/__tests__/marks.test.ts` |
| keeping source, marks and tokens in step | `packages/edit/src/__tests__/sync.test.ts` |
| refusing an edit that would destroy evidence | `packages/edit/src/__tests__/guards.test.ts` |
| the accented witness across an edit | `packages/edit/src/__tests__/witness.test.ts` |
| the holding invariants | `packages/edit/src/__tests__/holdings.test.ts`, `tests/integration/holding-invariants.test.ts` |
| pages, zoom, the three views | `packages/layout/src/__tests__/zoom.test.ts`, `paginate.test.ts`, `anchor.test.ts` |
| the document's type scale, and 1:1 with his `.docx` | `tests/integration/document-type.test.ts`, `word-fidelity.test.ts` + the `check:document` gate |
| `.smdoc` v2 — saving and opening a document | `tests/integration/smdoc-container.test.ts` |
| `.smdoc` v1 — opening his older documents | `tests/integration/smdoc-v1.test.ts` |
| Word import and export | `tests/integration/word-surfaces.test.ts` |
| the editing surface: a click becomes a position | `tests/component/editor-surface.test.tsx` |
| the window: title bar per platform, ribbon buttons, icons | `tests/component/shell.test.tsx` |
| which ribbon groups fit at a given width | `apps/web/src/shell/__tests__/fit-groups.test.ts` |
| the navigation panel's tree | `apps/web/src/shell/__tests__/outline.test.ts` |
| commands, accelerators and their buttons agreeing | `apps/web/src/shell/__tests__/registries.test.ts` |
| hostile input to the package reader | `tests/security/package-archive.test.ts` |

And the things only a browser can answer — that the page matches his `.docx` in
points, that nothing is clipped at any width, that every theme resolves, that
editing works end to end — are the gates in `tools/`, listed in `CLAUDE.md`.

## Running them

```bash
npm test                  # unit + integration + component + security
npm run test:unit
npm run test:integration
npm run test:component
npm run test:security
npm run test:e2e          # needs a build; see tests/e2e/README.md
npm run test:watch        # unit + component, on change

npm run check             # the gates, in series, plus typecheck and the tests
```

## Adding a test

Put it in the cheapest tier that can catch the bug. A pagination rule belongs in
unit; that pagination and the PDF export agreeing belongs in integration; the
page ruler appearing when you switch view belongs in component; opening a file
from the OS belongs in e2e.

If a bug reaches a user, the question to ask is not "which test failed" but
"which tier should have caught this, and why did it not exist there".
